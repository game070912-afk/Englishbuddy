# 语音输入（口语练习入口）

- 提出人：项目负责人（小胡）
- 日期：2026-10-02
- 状态：待排期

## 起源

上线当天试用对话页时提出：「这输入框竟然没有语音输入，后期把这个功能搞一下。」

## 为什么值得做

EnglishBuddy 的定位是「开口说话，说错了当场纠正」，但练口语的第一步——开口——目前只能靠打字。语音输入补上后，产品闭环才算真正成立：**说 → AI 听写 → 对话回复 → 纠错**。

## 初步方案设想（AI 起草，未评审）

两条路线，落地前需要对比：

| 路线 | 思路 | 优点 | 顾虑 |
| --- | --- | --- | --- |
| A. 浏览器 Web Speech API | `webkitSpeechRecognition` 直接在浏览器端识别 | 零成本、无需后端改动 | Chrome 支持好，Safari/火狐兼容性差；识别走 Google 服务，国内不可靠 |
| B. 智谱 GLM-ASR / 其他 ASR API | 前端 `MediaRecorder` 录音 → 上传 `/api/transcribe` → 转文字 → 复用现有对话链路 | 国内直连、可控制成本（GLM-ASR 按量计费，需查价格） | 多一个接口和密钥用量，录音上传需处理格式与大小限制 |

倾向：先做 A 的能力探测（不支持时按钮隐藏），B 作为国内主路线评估。与 ADR 0002 的「供应商可插拔」思路一致，转写层也应收在 `lib/api/` 单处。

## 验收设想

- 对话输入框出现麦克风按钮，按住说话松手即转文字填入输入框（可修改后发送）
- 不支持语音的环境优雅降级：按钮不出现，打字体验不变
- 转写结果为空 / 出错时给中文提示，不阻塞打字输入

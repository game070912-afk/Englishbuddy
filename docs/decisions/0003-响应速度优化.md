# ADR 0003：给 AI 调用加输出上限，并把接口排除出中间件

- 状态：**已采纳，待项目负责人复核**（AI 起草并执行）
- 日期：2026-10-03

## 背景

项目负责人反馈线上体感「回答太慢」。项目跑在免费资源上（智谱免费模型 + Vercel Hobby），
不能靠加钱换性能，只能把能省的每一段等待挤掉。

先把「慢」拆成三段，否则就是在瞎调：

1. **首字延迟（TTFB）**：从点发送到收到第一个字，取决于模型加载 + 输入长度
2. **生成耗时**：输出是按 token 一个一个吐的，输出越长等得越久
3. **请求发出之前的自家开销**：我们的代码在调用模型之前做的每一件事，都算在用户等待里

## 决定

### 1. 给每次调用加 `max_tokens` 上限

| 接口 | 上限 | 依据 |
| --- | --- | --- |
| `/api/chat` | 320 | 提示词要求外教每次只说 2-4 句（约 100 token），320 留足余量 |
| `/api/correct` | 1600 | 输入最多 2000 字符，输出是「改后全文 + 最多 10 条问题」 |
| `/api/vocab` | 400 | 卡片 JSON 只有几十个 token |

这不是为了省钱，而是为了**让最坏情况可预期**：不设上限时模型偶尔发疯写长文，
用户就得干等十几秒，而且流式输出会让他看着一段不想看的内容慢慢刷出来。

### 2. 历史消息从「限条数」改成「限条数 + 限总字符数」

原来只限制最多 20 条，但 20 条长消息能塞进去几万字符。输入越长，模型开始吐第一个字之前
的等待就越久。现在多了 4000 字符的总预算，超出就从最旧的开始丢，**但至少保留最后一条**
（用户刚发的那句）。

### 3. 把 `/api` 排除出 `proxy.ts` 的匹配范围

这是本次**收益最大**的一处，也是最容易忽略的一处。

原来的 matcher 覆盖了所有路径，包括接口。于是每一次聊天请求的实际链路是：

```
浏览器 → proxy.ts（查一次 Supabase 刷新登录态）→ /api/chat（再查一次 Supabase）→ 智谱
                    ↑ 这一趟纯属重复
```

接口自己就会读登录态，中间件里那次查询白白多了一趟跨服务网络往返，而这段时间用户是在
干等的。

**代价**：刷新过期 cookie 只发生在页面导航时了。但 refresh token 本身依然在服务端照常生效，
接口拿到的用户身份不受影响；用户真正在浏览器里跳转页面时，proxy 会照常更新 cookie。
用一次几乎无感的取舍换掉每个 AI 请求的一次往返，划算。

## 没做的事（以及为什么）

- **没换更快的模型**：免费档能选的都是同一个量级的模型，换供应商要花钱，违背了项目零成本的前提
- **没做预热 / 保活**：Vercel Hobby 的函数空闲后会冷启动（约 1-3 秒），这是免费套餐的固定成本。
  真要解决得挂个外部定时 ping，属于运维负担，暂时不做
- **没砍得更狠**：`max_tokens` 压到 200 确实更快，但会出现回复被拦腰截断的风险。宁可慢一点，
  也不要给用户看半句话

## 复核点

- `proxy.ts` 的 matcher 排除 `/api` 后，登录态会不会在纯接口调用场景下不刷新？目前的判断是不会
  影响功能，但如果出现「用着用着掉登录」的现象，第一个该怀疑的就是这里
- 320 token 的上限是否会让长回复被截断？需要项目负责人实际聊几轮确认

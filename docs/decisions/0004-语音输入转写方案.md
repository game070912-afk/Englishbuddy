# ADR 0004：语音输入转写方案（百度短语音识别·英文免费额度）

- 状态：**已采纳**（2026-10-04 项目负责人拍板方案 1；已实现）
- 日期：2026-10-04

## 背景

语音输入是 EnglishBuddy「说 → AI 听写 → 对话回复 → 纠错」闭环的第一步（原始设想见 `docs/ideas/2026-10-02-语音输入.md`）。设想里列了两条路线：

- **A. 浏览器 Web Speech API**：零成本、无需后端，但识别走 Google 服务，国内无代理基本不可用
- **B. 录音上传 → `/api/transcribe` → ASR API**：国内直连、可控制成本，但多一个接口和密钥

项目负责人 2026-10-04 明确了两条硬约束：**零成本优先（不打算花钱，涉及付费必须先问）**，以及 **Web Speech API 不能当主路线**。

于是真正的选型问题变成：**国内到底有没有"零成本 + 国内可达"的语音转写方案**。查证结果（2026-10-04）：

| 方案 | 是否零成本 | 国内可达 | 备注 |
| --- | --- | --- | --- |
| Web Speech API | 是 | **否**（走 Google） | 只能当降级兜底 |
| 智谱 GLM-ASR-2512 | **否**，约 ¥0.015/分钟 | 是 | 智谱免费清单只有 GLM-4.7-Flash / 4.5-Flash / 4.6V-Flash，**ASR 不在内** |
| **百度短语音识别（英文）** | **是**，个人认证 3 万次额度，官方标注永久有效 | 是 | `dev_pid=1737` |
| 腾讯实时语音（英文） | 是，10 小时/月 | 是 | 走 WebSocket 流式，接入复杂度高一个量级 |
| 火山豆包 ASR | 是，约 10 小时/天 | 是 | 额度高，但控制台配置步骤多 |

> 顺带纠正原始设想里的一处判断：设想写「智谱 GLM-ASR 按量计费，需查价格」，查完确认它确实是**按分钟收费的付费项**，不属于智谱免费模型家族。

## 结论

选择 **百度短语音识别标准版（英文，`dev_pid=1737`）**，走免费额度。理由：

1. **零成本且确定**：个人认证即发放 3 万次免费调用额度，官方文档写明「首次登录语音技术控制台发放后**永久有效**」——不是阿里云百炼那种 90 天试用，对个人作品集是长期可用的量级
2. **国内直连**：`vop.baidu.com` 不依赖 Google，部署在 Vercel 上从国内访问也没有网络障碍
3. **接口最简单**：一次 HTTP POST 传完整音频（≤60 秒），不是 WebSocket 流式——对「按住说话、松手出文字」这种一次性短句场景，同步接口反而比流式更省事，也更容易写测试
4. **不引入新依赖**：纯 REST，Node 原生 `fetch` 即可，不需要装 SDK

同时明确：**路线 A（Web Speech API）不作为主路线**，仅保留为后续可选的渐进增强（待实测国内可用性后再决定是否实现）。

## 影响

### 1. 新增服务端接口 `/api/transcribe`

百度文档明确写了「**浏览器无法跨域请求百度语音服务器，因此无法直接调用 API**」——这正好与项目既有安全规则一致（密钥只在服务端、组件不得直接 fetch）。链路：

```
浏览器 MediaRecorder 录音 → 客户端转成 16kHz/16bit/单声道 WAV
  → POST /api/transcribe（我们的服务端，密钥只在这里）
  → 百度 server_api → 文本 → 回填输入框
```

转写客户端收在 `lib/api/`（延续 ADR 0001「AI 调用集中一处」与 ADR 0002「供应商可插拔」的思路），将来换 ASR 只改这一处。

### 2. 音频格式是本次最大的技术风险

百度只接受 `pcm / wav / amr / m4a`，要求 **16kHz、16bit、单声道、≤60 秒**。而浏览器 `MediaRecorder` 默认产出的是 `webm/opus`（Chrome）或 `mp4/aac`（Safari）——**百度都不收**（`m4a` 主要面向微信小程序录音，Safari 的 mp4 不算）。

因此必须在**客户端**做一步转码：`decodeAudioData` 解码 → 重采样到 16000 Hz → 编码成 WAV(PCM16)。放在客户端而不是服务端，是因为服务端转码要么依赖二进制工具（Vercel 上麻烦），要么多一次函数耗时，而浏览器 Web Audio API 天然能做这件事。

### 3. 免费额度的边界（诚实说）

- 3 万次是**一次性发放、永久有效**的额度，**不是每月重置**。作品集演示量（每天几十次）能用很久，但若被公开大规模访问会耗尽
- 耗尽后百度按量约 **¥0.0015/次**。项目负责人 2026-10-04 补了一句判断：**这个量级可以忽略，不值得再花时间纠结**——所以超出免费额度不再作为选型阻塞项
- 免费额度并发只有 **3**，需要做基础限流（可复用已有 `lib/api/usage-guard.ts` 的思路），避免「演示时几个人同时点就 429」

### 4. 隐私

录音只在用户按下麦克风时采集，转写完即弃，**服务端不落盘、不入库**。这既是隐私合规要求，也是作品集里能讲的设计点。

## 没做的事（以及为什么）

- **没做实时流式识别**：百度实时语音要走 WebSocket，复杂度高一个量级，而「按住说一句、松手出文字」不需要边说边出字
- **没选智谱 GLM-ASR**：它不在智谱免费模型清单内（约 ¥0.015/分钟），违背零成本前提
- **没把 Web Speech API 做进主路线**：负责人已明确国内不可靠。是否做降级兜底，等主路线跑通后再实测决定

## 复核点

- **60 秒上限**：前端必须在接近 60 秒时自动停止录音（建议 55 秒留余量），否则请求会被百度直接拒绝
- **重采样质量**：浏览器解码后重采样到 16k 这一处最容易出 bug，且直接决定识别准确率——这是最需要人工试听验证的地方
- **「永久有效」要眼见为实**：文档写的是发放后永久有效，建议负责人首次登录语音技术控制台时，在控制台里亲眼确认额度数字与有效期，别只信文档
